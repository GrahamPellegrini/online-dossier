Pipeline Modules

Each node has a narrow responsibility. The audit question is whether the handoff between nodes is reliable enough for replay.

  1. 1

    Quest capture

    Records RGB, depth, headset pose and hand pose for task and orbit sessions.

    Quest sensor capture
  2. 2

    Ingestion and MinIO

    Accepts uploads, stores raw inputs and exposes session artifacts for worker processing.

    MinIO object storage
  3. 3

    Hands23 hand detection

    Provides hand/object contact evidence and candidate boxes before object processing begins.

    Hands23 code and explanation
  4. 4

    SAM2 segmentation

    Turns candidate evidence into masks for orbit reconstruction and task-frame object tracking.

    SAM2 overview and code
  5. 5a

    PointCloudPCA

    Provides model-free task pose estimates when a trusted mesh is not available.

    Project pose measurements
  6. 5b

    FoundationPose with mesh

    Runs when a suitable mesh, mask and depth are available; this is the stronger route for mesh-backed replay.

    FoundationPose overview and code
  7. 6

    Qwen labels

    Supplies an object label from the crop; useful, but still dependent on mask quality.

    Qwen3-VL-4B-Instruct model
  8. 7

    DINOv2 and SigLIP

    Support visual identity checks. The current audit keeps DINOv2 and SigLIP rather than adopting DINOv3.

    DINOv2 ViT-S/14 model · SigLIP base model
  9. 8

    COLMAP mesh reconstruction

    Reconstructs object meshes from orbit capture frames for canonical mesh-backed replay.

    COLMAP tutorial and code
  10. 9

    Headset replay

    Consumes stored objects, tracks, meshes and masks so captured objects can be inspected in VR.

    Unity XR Interaction Toolkit

System Status

Confirmed steps come first, followed by demo patches, partial fixes and disabled work, then outcomes still to confirm. Open up to two cards at once. The side connections show where a working step still depends on unfinished follow-up.

Hands23: the starting pointA detected grip supplies the hand and object boxes that seed the rest of the pipeline.Module 3Confirmed

The live worker checks the separate Hands23 service and saves its detections before object processing. Missing detections now raise an error, instead of being mistaken for a recording with no object. A brief deliberate grip seeds the orbit route; task recordings use contact evidence to start tracking.

These boxes changed the architecture: SAM2 can now isolate both the hand and the object, so a separate SAM3 hand detector is no longer needed. A box is the starting region, not a finished mask or mesh.

Hands23 code and explanation

Grip-first orbit mesh generationThe reconstruction route produces real-scale meshes when a grip is detected and the orbit has usable visual detail.Modules 3, 4, 8Confirmed

Grip first, then slowly circle the object for the rest of the clip. Hands23 identifies the starting object; SAM2 follows its outline. Masked COLMAP matches visible features across the images and reconstructs a 3D point cloud. Open3D builds the surface, and Quest head poses set its scale in metres.

Candle and clock reconstructions are measured successes. This confirms the reconstruction method; it does not establish unattended upload-to-mesh automation for every session. The latest clock reconstruction was run and registered manually.

FoundationPose with a trusted meshThe mesh-backed service has run successfully; reliable tracking through hand occlusion still needs care.Module 5bConfirmed

FoundationPose was already implemented. The recorded activation blockers were the wrong GPU being almost full from another job, and a mesh loader expecting OBJ while registered assets used GLB. Moving the service to a GPU with room and supplying the expected mesh enabled real registration and more than 100 successful tracking calls.

The bottle trial still had 9 large rotation jumps in 112 transitions, mostly flip-and-recover pairs. Hand occlusion was a likely cause, not a proven diagnosis. A working container does not prove perfect tracking.

Default live task processing remains model-free while mesh matching is disabled. Borrowing a mesh for rendering does not rerun FoundationPose.

Without a trusted mesh, the remaining fallback issue is PointCloudPCA.

FoundationPose overview and code

SAM3 removal: SAM2 is sufficient for the current promptsHands23 supplies the boxes; SAM2 creates the object and hand masks.Modules 3, 4Confirmed

The earlier reference-image mesh route needed hand pixels removed before generating a mesh. SAM3 was also used for an object-presence check. It was removed after the Hands23-guided SAM2 route was evaluated; this was more than removing a duplicate model.

ModelPlain-language roleWhy this pipeline changed
SAM2Select a region using a point or box, then follow its pixels through video.Hands23 supplies an object box and a hand box. SAM2 makes separate object and hand masks; hand pixels are subtracted.
SAM3Find and segment concepts using text or example prompts.Previously used for hand removal and an object-presence check. Its hand mask failed on a real bottle recording; the presence score did not reliably distinguish a real grasp from a fake one.

SAM2 runs with two different prompts, producing two masks. Qwen performs the remaining held-object check. This keeps the pipeline simpler without claiming SAM3 is inferior for every task.

Episode naming endpointNames are built from existing object labels and capture dates, then served to Unity by session UUID.Modules 2, 6Confirmed

{object_key}_{counter}_{YYMMDD}

The server uses existing Qwen3-VL labels and, when available, canonical category or label data. It normalises supported terms, rather than asking another model to invent a task title. The counter starts at 00 for each object-key/date pair and grows beyond 99. The capture date prefers device-local time.

Mesh selection and headset replayMeshes can render in replay; the current task selection policy is a temporary shortcut.Modules 7, 9Fixed for demo
  • Rendering: demo sessions had meshes assigned manually. The clock bounding-box mismatch was corrected so Unity’s shape check accepts the mesh.
  • Orbit ownership: orbit replay uses its own registered reconstruction rather than another session’s mesh.
  • Task shortcut: every task object is currently served the latest mesh-bearing orbit registration, without checking object identity. Source orbit dimensions accompany the mesh; task tracks remain unchanged.
  • Matching disabled: SigLIP retrieval achieved 4/11 correct historical decisions; correct and incorrect scores overlap. Automatic matching remains switched off.
  • Still needed: validated identity and mesh-quality selection, mesh-backed pose estimation where appropriate, and headset checks of the latest API policy.

This patch joins display and storage; it does not make the borrowed mesh the right object or improve the recorded poses.

PointCloudPCA: pose fallback without a meshA partial view or noisy depth can make the estimated object position jump.Module 5aPartially fixed

This route estimates the centre and orientation of the visible depth points. If the visible patch changes, the estimated object can suddenly move even when the real object does not. The full object shape is unknown.

Slow candle: maximum frame-to-frame jump 0.153 m.

Fast clock: maximum frame-to-frame jump 1.053 m.

Table-contact Stanley cup: maximum jump 0.738 m.

These are recorded pre-guard measurements, not new results after the fix. During a confirmed grip, the deployed guard drops estimates more than 0.5 m from every available wrist/palm. Missing hand landmarks cannot be checked, and unheld objects are not covered by this rule.

Next: measure post-guard natural-motion performance and add justified motion, table-contact or temporal constraints. Robust fallback replay remains unconfirmed.

Automatic mesh matchingThe identity matcher stays off while false assignments remain unresolved.Module 7Disabled

The full mesh-selection situation is collected in Mesh selection and headset replay. This disabled branch is why normal live tasks do not automatically reach FoundationPose.

Replay orientation and interactionUnity-side facing, placement, size and grabbing still need refinement.Module 9Not confirmed
  • Align ghost replay with the viewer’s current facing direction at spawn.
  • Correct clock orbit mesh orientation.
  • Define placement when new recording stamps are added, and check their sizing.
  • Support both direct grabbing and Quest-style distance pointers.

These are reported follow-ups, not verified fixes. The latest mesh policy does not resolve them.

Dedicated Maestro server endpointThe IT Services request is submitted; there has been no follow-up response.Module 2Not confirmed

Maestro currently uses the shared university proxy. A dedicated endpoint is pending for EEAI 2026 and the presentation of the encapsulated edge-AI system. A dedicated endpoint is the intended infrastructure change, but successful operation after migration is not yet established.

After IT supplies it, validate headset URLs, HTTPS, uploads, metadata and mesh downloads together; changing the endpoint may expose integration problems.

DINOv3 encoder consolidationA single encoder could replace DINOv2 and SigLIP, but the corrected results do not justify adoption.Module 7Not confirmed

The aim is to simplify visual comparison and reduce model weight. DINOv3-S has 21.60M parameters and B 85.66M, versus 225.21M for the existing pair. The proposed replacement is not deployed.

The earlier test compared reused/self crops rather than independent hand-to-hand views, and some source sessions were empty or had wrong masks. That proxy could not establish real re-identification. The corrected evaluation restored the data and used independent crops; it is complete and supersedes that first test.

Foreground matching ranks known objects better, but still wrongly assigns an absent pen and remote. Next research needs independent held-out recordings, absent-object checks and reliable rejection of unknown objects; any adopted replacement must also preserve the identity pipeline’s spatial/time checks. Keep DINOv2 and SigLIP, and leave mesh matching disabled meanwhile.

Possible feedback and design decisions

  • Naming convention: should users keep the compact machine name, see a friendlier title, or add their own task title? Current names describe object records, not the action performed.
  • Offline Wi-Fi: distinguish connected, unstable and fully offline states with an explicit icon/message. Agree how queued uploads and unavailable metadata should appear; client behaviour still needs validation.

Why the plan moved, and what remains to agree

The original technical plan expected regular expert recording from June, labelled data and training preparation in July–August, and initial robot simulation results by October 2026. Dataset construction depended on a reliable VR capture/processing tool. Mesh work took approximately one month according to the project lead, followed by integration and tracking setbacks; this is not a measured breakdown of the whole delay.

The envisioned route is refinement → one controlled task collected in sufficient quantity and vetted → Kingswell case study → further collection and robotics inference. Sample count, coverage, quality thresholds, hardware integration and viva scheduling remain to agree. Hardware research is optional unless the agreed collection criteria require it.

Sources: technical delivery plan; EEAI acceptance letter; project audit evidence; Master’s viva preparation notes. No live presentation or demo requirement is assumed.
